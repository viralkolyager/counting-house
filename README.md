### 1. Суть доработки и ключевая идея алгоритма

Калькулятор читает числа из текста сразу в `Fraction` (минуя `float`), поэтому ошибок
округления нет вообще: `0.1 + 0.2` — это ровно `3/10`. Выражение разбирается
«сортировочной станцией»: стек операторов переводит запись в обратную польскую, второй
стек её вычисляет. Инвариант: в стеке операторов приоритеты не убывают снизу вверх
(до ближайшей скобки), поэтому всё, что сильнее нового оператора, лежит сверху
и выталкивается первым. Каждый токен попадает в стек и снимается с него не больше
одного раза — отсюда O(n). Рекурсии нет, так что 10^5 вложенных скобок не ломают программу.

* **Было:** вычисления во `float` — `0.1 + 0.2 = 0.30000000000000004`, последовательность
  Мюллера сходится к 100 вместо 5; в ипотеке точность `Decimal` задавалась глобально
  одной строкой `getcontext().prec = 50`, и на сроке 1000 лет платёж получался равным
  процентам (долг не уменьшался).
* **Стало:** калькулятор на `Fraction` со стеками; точная формула `x_n` вместо
  прямой рекурсии; в ипотеке точность берётся из локального контекста и зависит от срока:
  `50 + n·log10(1 + r)` знаков.
* **Ключевой участок кода:** файл `calc.py`, строки `140–181` (`to_rpn`);
  файл `ex3_mortgage.py`, строки `69–89` (`precision_for`, `annuity_payment`).

### 2. Замеры сложности и производительности (до и после)

Замеры: `python bench.py`, Apple M5, Python 3.14.

**Калькулятор**, выражение из N = 10^6 дробей вида `1/2+1/3+-5/6+…` (точная сумма — 0):

| Метрика | Исходная версия (`float`) | Моя версия (`Fraction`) | Теоретическая оценка |
| :--- | :---: | :---: | :---: |
| **Время выполнения (сек)** | `2.514` | `3.800` | $O(N)$ |
| **Число операций** (токены + стек + арифметика) | `19 999 973` | `19 999 973` | $O(N)$ |
| **Ответ** | `≠ 0` (ошибка) | `0` (точно) | — |

Линейность видна по росту: на 10^3, 10^4, 10^5, 10^6 слагаемых — 0.005, 0.033, 0.352,
3.800 с, ровно 20 операций на слагаемое при любом N. `Fraction` медленнее `float`
всего в 1.5 раза и при этом не ошибается.

**Точное x_n в задаче Мюллера**, n = 10^4:

| Метрика | Исходная версия (рекурсия во `Fraction`) | Моя версия (формула `exact(n)`) | Теоретическая оценка |
| :--- | :---: | :---: | :---: |
| **Время выполнения (сек)** | `1.100` | `0.0004` | рекурсия $O(n^3)$, формула $O(n^2)$ |
| **Число операций** | `9 999` вызовов `f` над числами до 7000 цифр | 4 возведения в степень + 1 `gcd` | — |

При n = 3·10^4 рекурсия считает 23.3 с, а формула — 0.003 с. Числитель и знаменатель
x_n имеют ~0.7·n цифр. Рекурсия делает n шагов, и на каждом `Fraction` сокращает дробь
через `gcd` таких чисел — это O(n²) на шаг, итого O(n³) (n вырос в 3 раза — время в 21 раз).
Формула делает один `gcd` в конце — O(n²) с маленькой константой.

**Ипотека:** график на 120 000 строк строится за 0.083 с (0.7 мкс на строку), O(n).

Память замерять необязательно.

**Главное узкое место (bottleneck) моего решения:**
по профилировщику (`cProfile`, N = 10^5) больше всего времени уходит на `tokenize`
(посимвольный цикл на Python, `calc.py`, строки 81–137) и на `Fraction(tok.text)`
в `calc.py`, строка 212: конструктор `Fraction` разбирает каждую строку регулярным
выражением. Если в выражении дроби с растущими знаменателями (например, сумма
1/1 + 1/2 + … + 1/n), узким местом становится сокращение дробей в строке 221:
знаменатели растут, и `gcd` дорожает.

1. **`test_very_long_loan`** (`tests/test_mortgage.py`) — проверяет кредит на 1000 лет.
   При фиксированной точности `Decimal` платёж выходил равным процентам, и долг

2. **`test_deep_nesting_without_recursion`** (`tests/test_calc.py`) — проверяет
   100 000 вложенных скобок. Ловит рекурсивный разбор, который упал бы с `RecursionError`.
3. **`test_power_is_right_associative`** и **`test_extra_closing_bracket_message`**
   (`tests/test_calc.py`) — проверяют, что `2^3^2 = 512`, а не 64, и что на `1) + (2`
   выдаётся понятная ошибка, а не падение с `IndexError`.

Кроме того: пустой ввод, деление на ноль, неверные типы (`float` и `int` вместо `Decimal`
для денег запрещены), `NaN`/`Infinity`, срок 0 лет, кредит в одну копейку, нулевая ставка,
линейность счётчика операций.

**Мутационная проверка.** В копию проекта по очереди вносились 11 поломок (поменять
ассоциативность, перепутать операнды вычитания, округлять платёж к ближайшему,
удвоить проценты, перепутать `y` и `z` в формуле Мюллера и т. д.) — тесты падают
на каждой.

## Ответы к упражнениям

### №1. Машинное эпсилон

Делим `eps` пополам, пока `1.0 + eps/2 != 1.0`.
Результат: `2.220446049250313e-16 = 2**-52` — совпадает с `sys.float_info.epsilon`.
Для одинарной точности: `2**-23 ≈ 1.19e-07`.

### №2. Рекурсия Мюллера

`f(y, z) = 108 - (815 - 1500/z) / y`, `x0 = 4`, `x1 = 4.25`.

**а)** Во `float` получается `x30 = 100.0`.

**б)** Неподвижные точки — корни `(x-3)(x-5)(x-100) = 0`. Подстановка `x_n = u_{n+1}/u_n`
даёт линейную рекурсию с решением `u_n = a·3^n + b·5^n + c·100^n`. Начальные условия
дают `a = b`, `c = 0`, то есть

```
x_n = (3^(n+1) + 5^(n+1)) / (3^n + 5^n)  →  5
```

Точное значение `x30 ≈ 4.9999995578522585`. (В тексте курса написано «должно было
получиться 4» — это опечатка: 4 — начальное значение, предел равен **5**.)

**в)** `c = 0` выполняется только в точной арифметике. Из-за округления появляется
крошечная составляющая `c·100^n`, которая растёт в `20^n` раз быстрее правильной.
Точка 100 притягивающая, точка 5 — отталкивающая, поэтому ошибки округления
неизбежно уводят последовательность к 100.

### №3. Ипотека

```bash
python ex3_mortgage.py 3000000 12 15          # S, x% годовых, y лет
python ex3_mortgage.py 3000000 12 15 --no-show --no-table --out-dir plots
```

- платёж `P = S·r / (1 − (1+r)^−12y)`, `r = x/12/100`, округлён вверх до копейки;
- последний платёж закрывает остаток и немного меньше остальных;
- выводит переплату, таблицу (остаток, платёж, проценты, основной долг);
- сохраняет графики `balance.png` и `payments.png`.

Пример: 3 000 000 ₽ под 12% на 15 лет → платёж 36 005,05 ₽, переплата 3 480 904,84 ₽.

Из-за округления платежа вверх очень длинные кредиты гасятся раньше срока: лишняя
доля копейки каждый месяц тоже идёт в основной долг. Например, на 100 лет — 1198
платежей вместо 1200.

### №4. Decimal и Fraction

- `Decimal` с точностью 28 знаков тоже уходит к 100 — это всё ещё арифметика
  с округлением. Нужно больше ~50 знаков, чтобы `x30` был верным.
- `Fraction` считает точно: `x30 = 2328306745375394431036/465661390253305305137`,
  и это в точности совпадает с аналитической формулой.
